## 问题与修复

旧版把完整 JSON 的十六进制文本拼进 B-tree 主键，64 KiB 合法证据会触发数据库索引键错误，回滚同一结果事务中的全部写入。

新键为 `v2:` 加 64 位 SHA-256 十六进制摘要，固定 67 个 ASCII 字符。摘要输入包含版本域、范围 ID、资产 ID、事件类型、上海自然日和规范化证据；job ID 不参加同日事件身份。原始证据继续完整写入原有 `detail`，不截断、不用摘要替换。事件类型、资产事实、来源缺失规则和 API 字段含义未调整；`dedupe_key` 的值现在有版本前缀，客户端不能按旧内部格式解析它。

规范化仅用于键：对象字段顺序不影响身份；IP_CHANGED 的 before/after 各自按字符串集合排序去重，前后方向不互换；NEW_ASSET 的 sources 按集合处理。其他数组保留顺序，Unicode 文本不做模糊归一化，大整数不经 float64；数字文本 1 与 1.0 没有额外合并。首个成功写入事件保留自己的原始 detail。

编码后的单条 detail 上限明确为 **256 KiB**（含 JSON 元数据）；64 KiB 证据与长主机名可用。超限或无法编码返回明确错误，不输出证据内容，也不静默丢弃事件。超限仍会使调用者事务失败，这是明确输入错误，而不是承诺任意大小都可提交。

## 兼容与发布限制

旧键保持不可变；新写入先在同一事务中预约唯一摘要键，再查同资产/类型/上海日期的旧键并比较解码后的规范化证据。若旧记录等价，则只保留摘要预约而不重复创建事件。新进程间的并发由数据库唯一键协调。

**后续发布必须停止所有旧版事件写入进程，包括 Web 导入与 worker，再统一切换。** 本次不部署。旧二进制不识别新键，不支持新旧写入者混跑；索引的 Down 测试成功不代表旧二进制可在同日无重复风险地接管新数据。回退程序需要匹配的数据恢复/去重方案，不能自动删新键或直接滚动回旧进程。

旧键兼容增加一次索引查询和一个索引的写入成本；没有进行前后性能压测，不能宣称吞吐提升。迁移会建索引，实际生产耗时、锁影响、备份及发布窗口需在获得生产授权后另行评估。SHA-256 提供实用的固定长度身份，未宣称数学上不存在碰撞。
